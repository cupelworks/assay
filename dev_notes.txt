2. Storage
When you add persistence, don't reach for a cloud-specific store (DynamoDB, Firestore). Use:
	•	PostgreSQL via asyncpg or SQLAlchemy — runs anywhere
	•	Or abstract behind a RunRepository interface so the backing store is swappable
3. Structured logging — not vendor-specific sinks
Write JSON logs to stdout. Every major cloud (CloudWatch, Stackdriver, Datadog, Loki) ingests stdout JSON. Don't use cloud-specific logging SDKs.

4. Test plan execution freezing
	•	Add test_plan_id to TestRunModel so a run can be attributed to a specific plan execution (currently a run only
	points at test_set_entry_id / test_id, with no way to tell which plan triggered it).
	•	CORRECTION (superseded from the original version of this note): do NOT block changes to a plan's TestPlanEntryModel
	links (add/remove test sets) once it has runs. Originally this note said to freeze those links with a 409 the moment
	the plan has any run, mirroring the entry-level "freeze at execution" pattern — that reasoning turned out to be wrong.
	It assumed the audit trail of "what a plan tested" gets derived by walking the live TestPlanEntryModel → TestSetModel →
	TestSetEntryModel graph after the fact, so a mid-execution unlink would supposedly cause the plan's declared membership
	to stop matching what's in flight. It doesn't: TestRunModel has no FK to TestPlanEntryModel, only to the test_set_entry
	(already frozen once it has a run) and, with this note's change, test_plan_id directly. Unlinking a test set doesn't orphan
	or invalidate any run that already exists — those runs already captured everything they need, independent of whether the
	junction row still exists. There is nothing left to protect by freezing the link.
	•	Leaving TestPlanEntryModel editable post-execution is also what makes "run live" (see note 5) actually mean something
	on a second or later execution — that mode's whole point is picking up whatever's currently linked, including sets added
	or removed since the last run. Freezing membership at first run would collapse the replay/live distinction in note 5 into
	a single mode.
	•	Do NOT try to freeze or snapshot the linked test sets' own content (renames, added/removed entries) either. That
	would collateral-freeze a shared test set for every other plan that also links it, and it's unnecessary: the true
	immutable audit trail of "what a plan actually tested" already exists for free via TestRunModel → TestSetEntryModel,
	since entries are frozen the moment they have a run.
	•	GET /test-plans/{id}/entries should stay a live view of current test set state — don't conflate it with the audit
	trail. If a frozen "what did this campaign actually test" view is needed, build it as a separate read
	(e.g. GET /test-plans/{id}/runs) deriving directly from the plan's TestRunModel rows, not by snapshotting membership
	at link or execution time.

5. Re-executing a test plan: replay vs. live
	•	A plan can be executed more than once over its life, potentially with different live test-set scope each time
	(test sets keep evolving between executions). At re-execution time, give the user an explicit choice: replay a specific
	past execution (same frozen entries as that run — apples-to-apples comparison, e.g. did the model regress on a fixed
	benchmark), or run the current live scope (fresh fan-out from the plan's currently linked test sets, picking up anything
	added/removed since).
	•	Don't hardcode this as a binary "first execution vs. live" choice — generalize to "replay any specific past execution."
	A plan executed 5 times has 5 distinct historical scopes, each independently replayable, not just one special "first time"
	bucket.
	•	test_plan_id alone on TestRunModel (see note 4) tells you which plan a run belongs to, but not which specific past
	execution event/batch it was part of — multiple execution batches for the same plan would share the same test_plan_id,
	making "list past executions, pick one to replay" fragile to infer from timestamps alone. To support this cleanly, add
	an explicit grouping entity: a TestPlanExecutionModel (one row per trigger event, its own created_at) with a
	test_plan_execution_id FK on TestRunModel. Then "replay execution N" = create fresh TestRunModels against the same
	test_set_entry_ids referenced by that TestPlanExecutionModel's existing runs; "run live" = fan out fresh from the current
	TestPlanEntryModel → TestSetModel → TestSetEntryModel graph, same as the very first execution did.
	•	Status check (as of this note): none of the above required a code change to existing freeze logic. The plan-level
	freeze discussed and retracted in note 4 was never implemented — add_test_sets_to_test_plan_by_id has always had only
	three guards (plan exists, test sets exist, no duplicate link), no "has runs" check. The entry-level freeze that does
	exist today (_check_test_set_entry_has_no_runs_or_409, _check_test_set_entries_have_no_runs_or_409,
	_check_given_test_set_entries_have_no_runs_or_409 — all scoped to TestSetEntryModel / test set deletion) is untouched
	by notes 4 and 5 and remains correct as-is. test_plan_id does not yet exist on TestRunModel either.
